# コースの追加方法

コースは「データ」です。`src/courses/` にファイルを 1 つ足し、`registry.ts` に 1 エントリ書けば一覧に並びます。コンポーネントを触る必要はありません。

一覧に出す情報（タイトル・説明・アイコン・レッスン数）は `registry.ts` に、本文（章とレッスン）は各コースファイルにあります。この分離のおかげで、ホーム画面は本文を読み込まずに描画でき、本文はコースを開いたときにはじめて読み込まれます。

## ファイル名

連番は付けません。表示順は `registry.ts` の配列順で決まるので、ファイル名に順序の意味を持たせると、間に 1 つ挟むだけで全部を付け替えることになるためです。

```
src/courses/
├── registry.ts        一覧（公開済み／追加予定）
├── basics.ts
├── data-analysis.ts
├── automation.ts
├── app-dev.ts
└── testing.ts
```

内容がわかるケバブケースにしてください。

## 1. 本文ファイルを作る

`src/courses/database.ts`：

```ts
import type { CourseContent } from "../types";

const content: CourseContent = {
  // packages: ["pandas"],          コース全体で使うパッケージ
  // files: { "data.csv": DATA },   コース全体で使う練習用ファイル
  chapters: [
    {
      id: "ch1",
      title: "第1章　sqlite3 で SQL を書く",
      lessons: [
        {
          id: "l1",
          title: "テーブルを作る",
          goal: "SQL でデータの置き場所を用意する",
          body: `...`,
          examples: [ /* ... */ ],
          exercise: { /* ... */ },
        },
      ],
    },
  ],
};

export default content;
```

タイトルやアイコンはここには書きません（`registry.ts` 側にあります）。

## 2. registry.ts に登録する

```ts
available(
  {
    id: "database",             // URL に使う。重複しないこと
    title: "データベースと SQL",
    icon: "database",           // src/icons.tsx の courseIcons のキー
    level: "実践",
    accent: "#d9a441",          // コース固有のアクセント色
    lessonCount: 12,            // レッスン総数
    description: "sqlite3 から始めて SQL を書き、SQLAlchemy を扱えるようにする。",
  },
  () => import("./database")
),
```

配列に並べた順がそのまま表示順です。

> `lessonCount` は、本文を読み込まずに進捗バー（`3/12` など）を出すために持っています。本文とずれていると開発モードで警告が出るので、レッスンを増やしたら合わせてください。

## 追加予定として先に告知する

本文がまだ無くても、一覧に「追加予定」として並べられます。`planned(...)` を使います。

```ts
planned(
  {
    id: "database",
    title: "データベースと SQL",
    icon: "database",
    level: "実践",
    accent: "#d9a441",
    description: "sqlite3 から始めて SQL を書き、SQLAlchemy を扱えるようにする。",
  },
  {
    plannedFor: "次回リリース",   // 省略すると「追加予定」と表示される
    topics: [
      "sqlite3 で SQL を書く",
      "SELECT / JOIN / 集計",
      "SQLAlchemy の基本",
    ],
  }
),
```

カードは破線・非活性で表示され、クリックできません。URL を直接叩かれても、公開済みのコースしか開けないようになっています（`findAvailableCourse` が `undefined` を返し、ホームに戻ります）。

### 公開に切り替える

本文ファイルを用意したら、`planned(...)` を `available(...)` に書き換えて `lessonCount` と `load` を足すだけです。UI 側の変更は要りません。

```diff
-planned(
+available(
   {
     id: "database",
     ...
+    lessonCount: 12,
   },
-  { plannedFor: "次回リリース", topics: [...] }
+  () => import("./database")
 ),
```

必要なら配列内の位置を動かして、公開済みのコースの並びに混ぜてください。

## レッスンの書き方

### body（解説）

Markdown で書きます。使える記法は markdown-it の標準どおりです（見出し・リスト・表・引用・リンク・コードブロック）。

TypeScript のテンプレートリテラルの中に書くため、**インラインコードのバッククォートは `\`` とエスケープが必要**です。コードブロックはバッククォート 3 つのかわりに `~~~` を使うとエスケープ不要で書けます。

````ts
body: `
Python の \`for\` は「中身を 1 つずつ取り出す」ループです。

~~~
for fruit in fruits:
    print(fruit)
~~~

> 引用は補足や注意に使います。
`,
````

#### 「もっと詳しく」（必須）

本文の末尾には、必ず `### もっと詳しく` を置いてください。**テストで必須にしています**（`src/__tests__/courses-content.test.ts`）。

解説は演習を解くのに要る分だけに絞ってあります。そのぶん、「サンプルには出てこないが、もっと良い書き方がある」という状態が起こります。学習者が自分で先へ進めるように、その入り口をレッスンごとに置くのがこの節の役目です。

```md
### もっと詳しく

<そのレッスンの範囲で、サンプルとは別のやり方・より適した道具・つまずきやすい前提を 1〜2 段落>

- [リンクの見出し（公式）](https://example.com/...)
- [リンクの見出し（公式・英語）](https://example.com/...)
```

- 書くのは **リンクだけにしない**。「何が載っているのか」「なぜそっちのほうが良いことがあるのか」を先に 1〜2 段落で書く
- リンクは一次資料（公式ドキュメント、PEP、MDN）に限る。ブログや記事は消えるので張らない
- 日本語版があるものは日本語版へ。英語しか無いものは見出しに `（英語）` と付ける
- `https` のみ（テストで弾いています）
- リンクを足したら `npm run verify:links` を回してください。到達できるか、`#anchor` が生きているかまで見ます

### examples（実行できるコード例）

```ts
examples: [
  {
    caption: "動かしてみる",          // ブロック見出し
    note: "**補足**を Markdown で書ける（省略可）",
    code: `
print("hello")
`,
    // runnable: false,             // ← 読むだけのブロックにする
    // packages: ["pandas"],        // ← このブロックで必要なパッケージ
    // files: { "data.csv": "..." },// ← 実行前に置くファイル
  },
],
```

ブラウザでは動かせないコード（サーバー起動、外部への HTTP 通信など）は `runnable: false` にしてください。編集不可の「読むだけ」ブロックとして表示されます。

### ヒントの書き方

ヒントで導くのは **解答例ではなく、考え方** です。`solution` はサイトが用意した書き方のひとつでしかないので、ヒントをたどると解答例の書き方に収束する、という作りにはしないでください。学習者が自分の書き方で正解にたどり着けることを目指します。

| 良い | 避ける |
|---|---|
| なぜそこが問題になるのかを説明する | 完成した式をそのまま書く |
| 使う関数やメソッドの**名前**を挙げる | コピーすれば通る 1 行を渡す |
| 「本文のこの表を見て」と参照先を示す | 解答例をなぞる手順を全部並べる |
| つまずきやすい点（`>` と `>=` の違いなど）を指摘する | 書き方をひとつに決めつける |

また、**課題を解くのに必要な文法は、必ずそのレッスンまでに本文で扱ってください。** 扱っていない道具が要るなら本文に説明を足します（本文で扱わない発展的な話は、上の「もっと詳しく」に置きます）。

#### 段階ヒント

複雑な課題では、`hint` を配列にすると **1 段ずつ開けるヒント** になります。学習者は「どこまで自力で進めて、どこで詰まっているか」に合わせて必要なぶんだけ開けます。

```ts
hint: [
  "何をする問題なのか（分解の視点）",
  "どこで判断を誤りやすいか（境界・順序・型）",
  "残りの手がかり（関連する章、道具の名前）",
],
```

- 目安は **3〜4 段**。1 段だけなら配列にせず、ただの文字列で書いてください（テストで弾いています）
- 使うのは**複雑な課題だけ**でよく、1 つの判断で解ける演習は文字列 1 本のほうが読みやすくなります
- 前の段を読んでいる前提で書きます。あとの段ほど具体的にしますが、最後の段でも解答例の写経にはしないでください

### exercise（自動採点つき演習）

```ts
exercise: {
  prompt: `課題文（Markdown）`,
  starter: `
def solve(n):
    pass
`,
  tests: `
g = globals()
f = g.get("solve")

check(callable(f), "solve という関数を定義できている")
if callable(f):
    check(f(3) == 9, "solve(3) が 9 を返す")
`,
  hint: "ヒント（Markdown、省略可）",  // ← 配列にすると段階ヒント
  solution: `解答例のコード（省略可）`,
},
```

## 採点コードの書き方

`tests` は、**学習者のコードを実行した直後に、同じ名前空間で実行される Python コード**です。次のヘルパーが使えます。

| ヘルパー | 用途 |
|---|---|
| `check(条件, "説明")` | チェック項目を 1 つ追加する。全部真ならクリア |
| `_stdout()` | そのレッスンで print された内容を文字列で取得する |
| `_shown()` | `show()` で図を表示したかどうか（データ分析コース用） |
| `_source()` | いまエディタに書かれているコードの文字列 |
| `run_pytest(...)` | 書いたコードをテストファイルとして pytest にかける（テストと品質コース用） |
| `run_mypy(...)` | 書いたコードをファイルとして mypy にかける（型ヒントと静的解析コース用） |
| `_replace_def(source, 名前, 差し替えるコード)` | トップレベルの関数・クラスを 1 つだけ差し替えたソースを作る（後述） |

### 守ってほしいこと

**1. 変数は `globals()` 経由で取る。**
学習者が変数を定義し忘れると `NameError` で採点が止まってしまいます。

```python
g = globals()
check("total" in g, "total という変数を作れている")
check(g.get("total") == 700, "total が 700 になっている")
```

**2. 関数は先に `callable` を確かめる。**

```python
f = g.get("solve")
check(callable(f), "solve という関数を定義できている")
if callable(f):
    check(f(3) == 9, "solve(3) が 9 を返す")
```

**3. メッセージは「何ができていればよいか」を書く。**
チェック項目はそのまま学習者へのフィードバックになります。失敗時に現在値を出すと親切です。

```python
check(g.get("total") == 700, f"total が 700 になっている（今は {g.get('total')}）")
```

**4. 期待値は必ず実際に計算して確かめる。**
練習用データを自分で書いた場合、期待値を手計算で書くとほぼ間違えます。手元の Python で一度回して合わせてください。

**5. 学習者のコードに依存した採点をしない。**
テストの中で学習者が書いた変数（データの定義など）を参照すると、それを消したときに採点自体が壊れます。判定に必要なデータはテスト側で用意してください。

**6. 個人が特定できる情報は例に入れない。**
名前は `山田` `佐藤` のような一般的なものを使います。

**7. 「書けているか」を個数だけで見ない。**
`check(len(asserts) >= 3, ...)` のような数え方だけだと、`assert True` を 3 つ並べた回答が通ってしまいます。**中身を確かめるには、実装を壊した版に対して学習者のテストを走らせ、落ちることを見ます。**

```python
NAIVE = """
def to_slug(title):
    return title
"""

bad = run_pytest(source=_replace_def(_source(), "to_slug", NAIVE), name="test_probe", quiet=True)
check(len(bad.failed) > 0, "書いたテストが、手抜きな実装を落とせる")
```

`_replace_def()` は、エディタが 1 枚しかない（実装とテストが同じファイルに並ぶ）この環境で、実装だけを差し替えるためのものです。**この形の採点をするときは、課題文にもそう書いてください**（隠れた条件で落とすと理不尽な採点になります）。

**8. 落としたい回答は `rejects` に置く。**
採点の抜けは「解答例が通るか」だけでは見つかりません。落としたい回答を書いておくと、`verify:exercises` が毎回「本当に落ちるか」を確かめます。

```ts
rejects: [
  {
    caption: "実装は正しいが、テストが中身を見ていない",
    code: `…`,
  },
],
```

### 書いたら必ず流す

```bash
npm run verify:exercises
```

確かめているのは 3 つです。

| 見るもの | 期待 |
|---|---|
| `solution` | 全項目クリアになる。**解答例は単体で動く形にしてください**（学習者はエディタの内容を丸ごと置き換えるため、前提のデータ定義や import も解答例に含める） |
| `starter` と `rejects` | クリアにならない（採点が課題文の要求を見ていない状態を防ぐ） |
| `examples` | 実行がエラーで止まらない。出力が `src/courses/__snapshots__/example-output.json` の記録と一致する |

わざとエラーを見せるコード例には `raises: true` を付けます（付けると逆に「エラーで止まること」を確かめます）。コード例の出力を意図して変えたときは `npm run verify:exercises -- --update-snapshot` で記録を取り直し、**差分が説明どおりかを目で見てから**コミットしてください。

採点の期待値は実際の計算結果なので、学習者のブラウザ内（Pyodide）と同じ版の Python で確かめる必要があります。`npm run verify:setup` で `.venv-pyodide/` を用意しておくと、`verify:exercises` が自動でそれを使います。

```bash
node scripts/audit-grading.mjs ch3/l7
```

採点がどこまで見ているかを調べる道具です（CI には入っていません）。解答例の数値をずらす・比較を反転する・文を消す、といった書き換えを試し、**それでも通ってしまう**ものを並べます。表示の文言や練習用データが通ってしまうのは構いません。**課題文が明確に求めていること**が通ってしまう場合は、`check()` を足すか `rejects` に回答例を残してください。

## pytest を使うレッスンを書く

「テストと品質」コースだけは、ブラウザ内で本物の pytest を走らせています。エディタがファイル 1 枚なので、`run_pytest()` が **いま書かれているコードをそのままテストファイル（`test_lesson.py`）として書き出して** pytest に渡します。実装は `src/lib/python-helpers.ts` にあり、ワーカーと `verify-exercises.mjs` の両方が同じソースを読み込みます。

```python
def test_average():
    assert average([10, 20, 30]) == 20


run_pytest()          # 手元で pytest コマンドを叩くのと同じこと
run_pytest("-v")      # 引数はそのまま pytest へ渡る
```

書き出すときに `run_pytest(...)` の呼び出し行だけを空行に置き換えます（pytest がファイルを import するため、残っていると入れ子になる）。**行番号は保たれる**ので、失敗レポートの行はエディタの行と一致します。

レッスンには `packages: ["pytest"]` を書いてください。

### 採点で使う

`tests` 側からは、キーワード引数つきで呼べます。

| 引数 | 用途 |
|---|---|
| `source=` | テストファイルの中身を明示する（`_source()` を渡すのが基本） |
| `modules=` | `{"scores": "..."}` でテスト対象のモジュールを差し替える |
| `name=` | 書き出すファイル名（既定 `"test_lesson"`） |
| `quiet=True` | pytest の出力を画面に流さない（採点では必ず付ける） |

戻り値の `_PytestOutcome` から `passed` / `failed` / `ok` / `results` / `output` が読めます。

**テストの演習は「壊した実装に当てて落ちるか」で採点します。** テストが書けたことより、そのテストがバグを捕まえられるかが本質だからです。

```python
BROKEN = """
def average(scores):
    return 0
"""

good = run_pytest(source=_source(), quiet=True)
check(good.ok, "書いたテストがすべて通る")

if good.ok:
    bad = run_pytest(source=_source(), modules={"scores": BROKEN}, quiet=True)
    check(len(bad.failed) > 0, "壊した版では落ちる（＝中身を確かめられている）")
```

`modules=` で差し替えたモジュールは、実行の前後で `sys.modules` から捨てられます。次の実行では `files` の内容に戻るので、採点が学習者の次の実行を汚しません。

> 練習用モジュールの名前は**レッスンごとに変えてください**。同じ名前で中身の違うモジュールを別のレッスンに置くと、同じセッション内で古いほうが使われることがあります。

## mypy を使うレッスンを書く

「型ヒントと静的解析」コースでは、同じ仕掛けで本物の mypy を動かしています。`run_mypy()` が、いま書かれているコードを `lesson.py` として書き出し、mypy にかけます。

```python
def greet(name: str) -> str:
    return "こんにちは、" + name


run_mypy()            # 手元で mypy ファイル名 を叩くのと同じこと
run_mypy("--strict")  # 引数はそのまま mypy へ渡る
```

書き出すときに `run_mypy(...)` の呼び出し行だけを空行に置き換えます（このアプリだけの名前なので、残すと mypy が「未定義」と報告する）。**行番号は保たれる**ので、指摘の行はエディタの行と一致します。

レッスンには `packages: ["mypy"]` を書いてください（wheel は約 6.6MB。ここに到達した学習者だけがダウンロードします）。

### 採点で使う

| 引数 | 用途 |
|---|---|
| `source=` | チェックする中身を明示する（`_source()` に文字列を足すのが基本） |
| `name=` | 書き出すファイル名（既定 `"lesson"`） |
| `quiet=True` | mypy の出力を画面に流さない（採点では必ず付ける） |

戻り値の `_MypyOutcome` から `ok` / `errors` / `codes` / `lines` / `output` が読め、`find(code=..., line=..., contains=...)` で絞り込めます。

**型の演習は「誤った使い方を捕まえられるか」で採点します。** 注釈が書いてあることではなく、その型が効いているかが本質だからです。

```python
report = run_mypy("--disallow-untyped-defs", quiet=True)
check(report.ok, "mypy が何も指摘しない")

# 学習者のコードの後ろに、わざと間違った呼び出しを足してかける
PROBE = "\n\ntotal_by_shop([('A', '100')])\n"
probe = run_mypy(source=_source() + PROBE, quiet=True)
check(probe.find(code="arg-type") != [], "金額に文字列を渡すと指摘される型になっている")
```

`list` や `dict` と書いただけの緩い型では、この確認が通りません。**「注釈の個数」を数える採点にしない**という原則（テストの個数を数えないのと同じ）を、型でも同じ形で守っています。

採点で `--disallow-untyped-defs` や `--strict` を使うときは、**課題文にもそう書いてください**（隠れた条件で落とすと理不尽な採点になります）。

## パッケージとファイル

`packages` と `files` は **コース → レッスン → ブロック** の順にマージされます。共通のデータはコース単位で書くのが楽です。

パッケージは必要なレッスンにだけ書いてください。`pandas` は読み込みに数秒かかるため、不要なレッスンに書くと待たされます。

使えるパッケージは `public/pyodide/` に wheel を置いたものだけです。増やすときは `scripts/pyodide-packages.mjs` の `WANTED` に名前を足して `npm run fetch:packages` を実行します（依存関係は自動でたどられます）。

現在の `WANTED` は `numpy` / `pandas` / `matplotlib` / `pytest` / `coverage` / `mypy` です。増やすと全学習者ではなく**そのレッスンに到達した学習者だけ**が追加のダウンロードをしますが、転送量に直接響くので、[デプロイ.md](デプロイ.md#転送量を減らしたいとき) の見積もりも合わせて更新してください。

Pyodide の配布物に無いパッケージが要る場合は、同じファイルの `EXTRA_WHEELS` に PyPI の URL と sha256 を書きます（mypy が要求する `mypy_extensions` と `pathspec` がこれにあたります）。取得元が違うだけで、扱いは配布物の wheel と同じです。sha256 を確かめてから `public/pyodide/` に置き、配信は自前の静的ファイルで行います。`pyodide-lock.json` に依存として書き足す処理も `fetch:packages` が行うため、レッスン側は `packages: ["mypy"]` と書くだけで済みます。
