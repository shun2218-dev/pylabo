# デプロイ

このアプリは **完全な静的サイト**です。サーバー側の処理は一切なく、`npm run build` が出力する `dist/` をそのまま配信すれば動きます。Vercel / Netlify / Cloudflare Pages / GitHub Pages / S3 など、静的ホスティングならどこでも構いません。

## Vercel の場合

リポジトリを Vercel にインポートするだけです。`vercel.json` に設定を入れてあるので、ダッシュボードでの追加設定は要りません。

| 項目 | 値 | 備考 |
|---|---|---|
| Framework Preset | Vite | `vercel.json` で指定済み |
| Build Command | `npm run build` | 同上 |
| Output Directory | `dist` | 同上 |
| Install Command | （既定） | `postinstall` で Pyodide 一式が用意される |
| リライト設定 | 不要 | ハッシュルーティング（`/#/c/...`）のため |

### ひとつだけ有効にする設定

プロジェクト設定 → **Environment Variables** → **Enable access to System Environment Variables** にチェックを入れてください。

これを有効にすると `VERCEL_PROJECT_PRODUCTION_URL` がビルド時に渡され、canonical・OGP・sitemap の絶対 URL が本番ドメインで自動生成されます。**環境変数を自分で設定する必要はありません。**

無効のままだと URL を決められず、canonical と OGP が出力されません。それに気づかず公開してしまわないよう、**Vercel の本番ビルドではこの状態を検知してビルドを失敗させます**（プレビューとローカルは警告のみ）。エラーメッセージにこの設定への案内が出ます。

独自ドメインを使う場合も、`VERCEL_PROJECT_PRODUCTION_URL` は「最も短い本番カスタムドメイン」を返すため、そのまま追従します。明示的に指定したいときだけ環境変数 `SITE_URL` を設定してください。

> プレビューデプロイでも canonical と OGP は**本番ドメイン**を指します。プレビュー URL が検索結果に出ないようにするためで、意図した挙動です。

### ビルド時に何が起きるか

1. `npm install` → `postinstall` が走る
   - `sync-pyodide.mjs` … `node_modules/pyodide` を `public/pyodide/` へコピー
   - `fetch-pyodide-packages.mjs` … pandas / matplotlib などの wheel を Pyodide 公式配布物から取得（sha256 検証つき）
2. `tsc -b` で型チェック
3. `vite build` で `dist/` を出力（`public/` の中身も `dist/` へコピーされる）
4. `scripts/generate-seo.mjs` が `robots.txt` と `sitemap.xml` を `dist/` に生成

**wheel の取得に 1 つでも失敗するとビルドが失敗します。** 欠けたまま公開すると、データ分析コースが実行時に「パッケージが見つからない」で壊れるためです。ビルドログに失敗したパッケージ名が出ます。

ビルド全体は 1 分程度です（Vercel の上限は 45 分）。

### デプロイサイズについて

`dist/` は約 35MB（うち 34MB が Pyodide ランタイムと wheel）です。

Vercel の「Static File uploads 100MB（Hobby）」という制限は **CLI でアップロードするソースファイル** に対するものなので、Git 連携でビルドする限り関係ありません。ビルド出力のファイル数に上限はありません。CLI（`vercel` コマンド）でデプロイする場合も、`.vercelignore` で `public/pyodide` を除いてあるため、送られるのはソースだけです。

### 帯域は要注意

学習者 1 人あたりの消費量です（初回、キャッシュなし。素の静的サーバーでの実測値）。

| 何をするか | 転送量 | リクエスト数 |
|---|---|---|
| ホーム画面を見るだけ | 約 0.2MB | 4 |
| 文法・自動化・アプリ開発コースを開く | 約 **14.9MB** | 16 |
| データ分析コース（pandas まで） | 約 **21.5MB** | 21 |
| データ分析コース（matplotlib まで） | 約 **29.5MB** | 29 |

Pyodide のランタイム（約 12MB）と wheel がそのまま流れるため、一般的な Web アプリよりかなり大きくなります。

**枠を使い切る目安**（Hobby の 100GB を丸ごとこのアプリに使える場合）

| コース | 月あたり |
|---|---|
| 文法・自動化・アプリ開発 | 約 6,900 人 |
| データ分析（matplotlib まで） | 約 3,500 人 |

Edge Requests（Hobby は 100 万/月）は 1 人あたり最大 29 回なので、先に尽きるのは必ず転送量のほうです。

#### 見積もるときの注意

- **Fast Data Transfer の枠はアカウント（チーム）単位で、全プロジェクトの合算です。** 同じアカウントで他のアプリを動かしているなら、その使用量を引いた残りが実際に使える分になります
- **Hobby には従量課金がありません。** 上限に達すると、ドキュメントの記載どおり「30 日経つまでその機能を使えない」状態になります。同じアカウントの他プロジェクトにも影響しうるので、公開範囲が読めないうちは Vercel Authentication で閲覧者を絞るか、GitHub Pages のように別枠のホスティングへ置くほうが安全です
- 2 回目以降の訪問では `vercel.json` のキャッシュ設定により転送はほぼ発生しません。効いてくるのは新規訪問者の数です

#### 転送量を減らしたいとき

いちばん効くのは wheel です。matplotlib 一式で約 9MB あり、これはデータ分析コースの第3章以降でしか使いません。パッケージはレッスン単位で指定しているので、**そこまで到達しない学習者はダウンロードしません**。さらに削るなら `scripts/fetch-pyodide-packages.mjs` の `WANTED` を見直してください。

## GitHub Pages の場合

転送量の事情は Vercel とほぼ同じです。**「GitHub Pages なら気にしなくてよい」ということはありません。**

| | Vercel (Hobby) | GitHub Pages |
|---|---|---|
| 月間転送量 | 100GB | 100GB（**ソフトリミット**） |
| 数え方の単位 | **アカウント（チーム）単位で全プロジェクト合算** | サイト単位 |
| 超えたとき | 従量課金、または上限で停止 | 配信を断られる場合がある／GitHub から改善の連絡が来る |
| 公開サイトの容量 | 実質制限なし | **1GB 以下**（本アプリは約 35MB） |
| キャッシュヘッダー | 自由に設定できる | **設定できない**（実測で `max-age=600` 固定） |
| 商用利用 | **Hobby は不可**（Pro 以上が必要） | **不可**（オンラインビジネスや SaaS の無料ホスティングとしては使えない） |
| 超過したとき | **Hobby はその機能が 30 日間使えなくなる**（従量課金なし）／Pro は従量課金 | 配信を断られる場合がある |

数えかたの単位が違うのが実務上いちばん効きます。Vercel の 100GB は**アカウント全体**の枠なので、同じアカウントで他のプロジェクトを動かしていれば、その分がこのアプリの取り分から引かれます。GitHub Pages は**サイト単位**の記載なので、他のリポジトリの Pages とは別枠と読めます。

キャッシュヘッダーを設定できない点は、実害は小さいです。GitHub Pages は ETag を返すので、10 分を過ぎても再訪問時は `304 Not Modified` になり、34MB の本体が再送されることはありません。ヘッダーだけの往復が増えるぶん、初回以降の体感がわずかに遅くなる程度です。

### 置き方

ビルド成果物（約 35MB）を `gh-pages` ブランチにコミットして回すと、更新のたびに履歴が膨らみます。**GitHub Actions でビルドして Pages へ直接デプロイする**方式にしてください。リポジトリ側は今のまま（`public/pyodide/` は gitignore）で構いません。

```yaml
# .github/workflows/deploy.yml（参考）
name: Deploy to GitHub Pages
on:
  push:
    branches: [main]
permissions:
  contents: read
  pages: write
  id-token: write
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
      - run: npm ci          # postinstall で Pyodide 一式が用意される
      - run: npm run build
      - uses: actions/upload-pages-artifact@v3
        with:
          path: dist
  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: github-pages
    steps:
      - uses: actions/deploy-pages@v4
```

プロジェクトサイト（`https://<user>.github.io/<repo>/`）に置く場合は、次節の `base` 設定が必要です。

## SEO まわり

`npm run build` で次が生成・出力されます。

| 出力 | 内容 |
|---|---|
| `index.html` | title / description / canonical / OGP / Twitter Card / theme-color |
| `og-image.png` | 1200×630 のシェア用画像 |
| `favicon.svg` `apple-touch-icon.png` | ファビコン |
| `site.webmanifest` | ホーム画面に追加したときの表示 |
| `robots.txt` `sitemap.xml` | クロール設定とサイトマップ |

公開先の URL は `SITE_URL` で指定します（Vercel では `VERCEL_PROJECT_PRODUCTION_URL` から自動で決まるため、通常は設定不要です）。canonical・OGP・sitemap の絶対 URL がこの値になります。

**決められないときは、絶対 URL が必要なタグと `sitemap.xml` を出力しません。** 既定値を置いて当てずっぽうの URL を焼き込むと、canonical が自分のものでないサイトを指し、検索結果から落ちる可能性があるためです。ビルド自体は通り、警告が出ます。

### 検索エンジンから見えるページは「/」だけです

このアプリは **ハッシュルーティング**（`/#/c/basics/ch1/l1`）を使っています。`#` 以降は検索エンジンに送られないため、**個々のレッスンは別ページとして扱われません**。sitemap.xml も `/` の 1 件だけです。

レッスン単位で検索流入を狙う段階になったら、次の対応が必要になります。

1. ルーティングをパス方式（`/c/basics/ch1/l1`）に変える
2. ホスティング側に SPA フォールバック（すべてのパスで `index.html` を返すリライト）を設定する
3. 各レッスンで `<title>` と `<meta name="description">` を書き換える
4. 必要なら静的な HTML を事前生成する

現時点では「アプリのトップが 1 ページ検索に出ればよい」という想定なので、構成を単純に保つほうを選んでいます。

## そのほかのホスティング

### サブパスに置く場合

`https://example.com/pylabo/` や GitHub Pages のプロジェクトサイトのように、サブディレクトリへ置くときは `vite.config.ts` に `base` を足してください。Pyodide の読み込み先は `import.meta.env.BASE_URL` から組み立てているので、これだけで追従します。

**あわせて `SITE_URL` にもサブパスを含めてください。** canonical・OGP・sitemap の絶対 URL がここから作られるため、サブパスが抜けると誤った URL を指すことになります。

```ts
export default defineConfig({
  base: "/pylabo/",
  // ...
});
```

### 必要なサーバー設定

- **リライトは不要**（ハッシュルーティングのため、常に `/` が返れば動きます）
- `.wasm` を `application/wasm` で返せること（多くのホスティングは既定で対応しています）
- 特別なヘッダー（COOP / COEP）は不要です。このアプリは SharedArrayBuffer を使いません

### 手元で本番同等の確認をする

```bash
npm run build
```

```bash
npx serve dist
```

`vite preview` ではなく素の静的サーバーで開くと、ホスティング環境に近い状態を確認できます。
