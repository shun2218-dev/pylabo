# コースロードマップ

今後追加するコースの候補と、その優先順位をまとめたものです。

判断の軸は **「実務で詰まる頻度 × 独学で身につきにくさ」** です。文法は本や記事で拾えますが、テストの書き方・型の運用・環境の切り分けあたりは、体系立てて教わる機会が少ないわりに現場で毎日効いてきます。そこから先に埋めます。

## 公開済み

| コース | レベル | ねらい | 収録 |
|---|---|---|---|
| **テストと品質** | 実践 | 壊れたらすぐ気づける状態を作る。書き捨てスクリプトから抜け出す最初の一歩 | assert とミニランナー自作 / pytest / 例外と approx / parametrize / フィクスチャ / モック / テストしやすい設計 / カバレッジ / TDD / 回帰テスト（12 レッスン） |
| **型ヒントと静的解析** | 実践 | 実行前に間違いを見つける。型を「設計の道具」として使う | 型ヒントと mypy / コレクション・None / Callable / dataclass・TypedDict / Literal・Enum / ジェネリクス / Protocol / strict と設定 / ruff と ast / 既存コードへの導入（12 レッスン） |

> ruff は Rust 製の実行ファイルでブラウザ内では動かないため、コマンドは「読むだけ」で示し、代わりに `ast` で未使用 import の検出（F401 相当）を自作する形にした。mypy は Pyodide に wheel があり、**本物をブラウザで動かせる**（`run_mypy()`）。

| 順 | コース | レベル | ねらい | 収録予定 |

## 棚卸しのタイミング

**「追加予定」が 3 本以下になったら、候補を洗い直す。** コースを 1 本公開するたびに残りは減るので、そのたびにこの節を見て、下の表を更新するかどうかを判断します。

見直すときにやること。

1. 未採用の候補の**保留の理由がまだ生きているか**を確かめる（ブラウザで動かせない、題材が用意しにくい、といった理由は、同梱パッケージや自作で動かす形が見つかると解消することがある）
2. **新しい候補を足す**（Python 側の変化、利用者からの声、公開済みコースで「ここは別コースにしたい」と感じた箇所から）
3. 採用するものを決め、`registry.ts` に `planned(...)` として並べる

採否は勝手に決めず、**候補と理由を並べて提案する**こと。何を学びたいかは利用者側の話で、こちらの都合で決めるものではありません。

## 追加するときの手順

1. `src/courses/registry.ts` に `planned(...)` で告知する（本文はまだ不要）
2. 本文ができたら `src/courses/<name>.ts` を作る
3. `planned(...)` を `available(...)` に書き換える

詳細は [コースの追加方法.md](コースの追加方法.md) を参照してください。

## 1 コースの目安

- **レッスン数** 6〜16。1 レッスンは 5〜10 分で終わる分量
- **章立て** 3〜4 章。最後の章は「卒業制作」として、それまでの内容を組み合わせる
- **演習** 各レッスンに 1 つ。自動採点のチェック項目は 3〜6 個
- **ブラウザで動かせない題材** は「読むだけ」ブロックにし、仕組みの部分は素の Python で自作して動かす
