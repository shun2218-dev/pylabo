# コードレビュー観点

`main` と `develop` への直接コミットは行わず、すべて Pull Request 経由でマージします。レビューはこの観点表に沿って行い、指摘には重大度を付けます。

## 重大度

| ラベル | 意味 | 扱い |
|---|---|---|
| **blocker** | 壊れる／誤ったことを教える／情報が漏れる | 直すまでマージしない |
| **should** | 直したほうが明確に良い | 原則その PR で直す |
| **nit** | 好みの範囲、細かい表記 | 任意。指摘だけして流してよい |

「指摘のための指摘」はしません。**変更後のコードが動き、読め、あとで直せるか**だけを見ます。

---

## 1. 学習コンテンツ（`src/courses/`）

このアプリの中身そのものです。ここの誤りは、学習者に間違ったことを教えることになるため最優先で見ます。

- **blocker** 解答例をそのまま実行すると採点を通るか（`npm run verify:exercises` が通ること）
- **blocker** 解答例が単体で動くか（前提のデータ定義や `import` が含まれているか）
- **blocker** 採点の期待値が実際の計算結果と一致しているか（手計算で書いていないか）
- **blocker** 採点コードが学習者の書いた変数に依存していないか（消されると採点自体が壊れる）
- **blocker** 個人名・メールアドレスなど、特定につながる情報が例に入っていないか
- **should** 課題を解くのに必要な文法が、そのレッスンまでに本文で扱われているか
- **should** 「もっと詳しく」が、リンクの列挙だけになっていないか（何が載っているかを先に書く。一次資料のみ）
- **should** ヒントが答えそのものになっていないか（道具の名前と参照先まで。完成した式は渡さない）
- **should** ヒントが解答例をなぞる手順になっていないか（考え方を示し、別の書き方でも正解にたどり着けるか）
- **should** ブラウザで動かせないコードが `runnable: false` になっているか
- **should** パッケージ指定が必要なレッスンだけに付いているか（`pandas` は読み込みに数秒かかる）
- **nit** 表記ゆれ（全角・半角、用語の統一）

## 2. 正しさ

- **blocker** 例外・空配列・`null` など、端の入力で落ちないか
- **blocker** 非同期処理の後始末（`useEffect` のクリーンアップ、購読の解除、`PyProxy` の `destroy`）
- **blocker** `localStorage` など外部の値を、壊れている前提で読んでいるか
- **should** 状態の持ち主が 1 か所に決まっているか（同じ情報を 2 か所で持っていないか）
- **should** 変更した箇所にテストがあるか。無いなら、なぜ不要かが説明できるか

## 3. 設計

- **blocker** コンテンツ（データ）と UI（表示）の分離が崩れていないか。コースを増やすのにコンポーネントを触る必要が出ていないか
- **should** 公開している型が実態と合っているか（`any` で逃げていないか）
- **should** 同じことを 2 か所に書いていないか。ただし **早すぎる共通化はしない**
- **should** 変更の影響範囲が読めるか（1 つの PR に無関係な変更が混ざっていないか）

## 4. パフォーマンス

- **should** 初期表示のバンドルに、コース画面でしか使わないものが入っていないか
- **should** 重い処理がメインスレッドに戻っていないか（Python の実行は必ず Worker）
- **nit** `useMemo` / `useCallback` が、実測なしに増えていないか

## 5. UI・アクセシビリティ

- **blocker** キーボードだけで操作できるか（ボタンが `div` になっていないか）
- **should** アイコンは lucide の SVG か（絵文字を使っていないか。フォント依存で大きさが揃わない）
- **should** ダーク・ライト両方で読めるか
- **should** 画面が狭いときに崩れないか
- **nit** 余白・角丸などがトークン（`src/styles/_tokens.scss`）から外れていないか

## 6. セキュリティ・プライバシー

- **blocker** `dangerouslySetInnerHTML` に、同梱コンテンツ以外の入力が流れ込んでいないか
- **blocker** 鍵・トークン・個人情報がコミットされていないか
- **should** 外部への通信を実行時に増やしていないか（依存は npm 管理、実行時 CDN なしの方針）

## 7. ビルドと運用

- **blocker** `npm run typecheck` `npm test` `npm run build` `npm run verify:exercises` がすべて通るか
- **should** 生成物（`public/pyodide/`、`dist/`）がコミットされていないか
- **should** 依存を足したなら、その必要性が説明できるか（初期バンドルへの影響を含む）

---

## レビューの進め方

1. PR を作成する（`gh pr create`）
2. レビューを実施し、重大度を付けてコメントする
3. **blocker** と **should** を修正して push する
4. CI が通ったらマージする（`gh pr merge --merge`。履歴を残すため squash はしない）

feature ブランチは `develop` へ、リリースは `develop` → `main` へ。マージ後はブランチを削除します。
